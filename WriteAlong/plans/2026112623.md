# Write Along — Implementation Plan

Source spec: [2026112623.md](file:///home/agents/Desktop/Personal%20Projects/Write%20Along/v4/prompts/2026112623.md)

**Starting point:** the repo is empty apart from the prompt. No `git`, no Node. Python 3.14 and Google Chrome are installed.

## 1. Key decisions

| Topic | Decision | Why |
|---|---|---|
| Build tooling | **Node (installed, v26.13.1 at `~/.local/node`) is dev-only.** The shipped app is vanilla ES modules and plain CSS with no runtime build. npm is used to fetch and bundle vendor libs once (`esbuild` for the CodeMirror bundle) and for tests (Playwright or `puppeteer-core` driving the installed Chrome). Python stays for template generation and validation. | The "static web app" requirement stays literal, with nothing needed at runtime beyond a static server. Node makes bundling CodeMirror and browser testing far easier. Network access to the npm registry is confirmed (Q1 resolved). |
| Markdown | Vendor **marked** (GFM) and **DOMPurify** into `vendor/`, pinned and committed. | The spec requires strict GFM. Vendoring keeps it offline-safe. Needs one-time network access to fetch the files (see Q1). |
| Code editor | Vendor **CodeMirror 6** as a prebuilt single-file bundle for md and css. Fallback: a `<textarea>` with a highlight overlay. | Gives syntax highlighting, line numbers, undo and search. |
| Rendering | One shared renderer, `render.js`. `read.html` and the editor preview both use it, in an `<iframe>` for the editor. | Guarantees "preview and print-to-PDF are identical". |
| PDF export | Browser print, with `@page` rules generated from `style.css`. | The spec says print-to-PDF from the browser. Avoids a heavy PDF library. |
| Paged layout | Paged.js-style pagination is deferred. Phase 1 uses CSS `@page`, `break-*` and running headers via `@page` margin boxes. | Chrome supports these. Native paging is more faithful than JS pagination. |
| Directory access | **File System Access API** (Chromium) with a fallback of `<input webkitdirectory>` import and a **.zip** download. | Opening a `.wa` folder is the core workflow. Firefox and Safari need the fallback. |
| Offline | Service worker with versioned precache, plus a manifest (installable PWA). | Matches "assets load only on first load or on editor update". |
| Templates | Real `.wa` directories under `templates/<id>.wa/`, plus `templates/index.json` generated by a script. | Matches "templates are just .wa directories". |

## 3. The `.wa` file format (Phase 0 spec, written first)

A directory `name.wa/`:

- **`content.md`**: strict GFM. No raw-HTML dependence. Allowed extras are limited to fenced "directives" (see below) so the file stays readable in any editor.
- **`style.css`**: all formatting.
- **`images/`**: embedded images, referenced relatively as `images/foo.png`.
- **`read.html`**: static, self-contained viewer.
- **`syntax.md`**: the syntax and AI-agent reference.

### 3.1 `style.css` naming convention

This is the heart of the design. It must be learnable by non-developers. The approach is **plain CSS plus CSS custom properties**, in two layers.

**Layer 1: a "settings" block of variables**, so people can restyle without knowing CSS:

```css
:root {
  --page-size: Letter;          /* Letter | A4 | A5 | Legal | 6in 9in */
  --page-margin: 1in 1in 1in 1in;
  --page-background: #fff;
  --text-color: #1a1a1a;
  --accent-color: #7a1f2b;
  --body-font: "EB Garamond", serif;
  --heading-font: "EB Garamond", serif;
  --code-font: "JetBrains Mono", monospace;
  --body-size: 11pt;
  --line-height: 1.5;
  --scale: 1.25;                /* heading modular scale */
}
```

**Layer 2: element selectors with a fixed, documented class vocabulary** (the position of every element):

```css
.page {}  .title {}  .subtitle {}  .author {}  .date {}  .abstract {}
h1 h2 h3 h4 h5 h6  p  blockquote  ul ol li  table  pre code
.callout  .callout-note/tip/warning  .figure  .caption  .toc
.header  .footer  .page-number  .cover  .pull-quote  .sidebar
```

Page furniture uses ordinary `@page` rules with margin boxes (`@top-center`, `@bottom-right`, and so on).

### 3.2 GFM-compatible extensions (kept minimal and degrade gracefully)

| Need | Syntax | Fallback in a plain editor |
|---|---|---|
| Classes on a block | Trailing attribute comment, `<!-- .callout-note -->` | Invisible HTML comment |
| Cover, title block | YAML front-matter (`title`, `author`, `date`, `subtitle`) | Standard front-matter |
| Page break | `---` plus `<!-- pagebreak -->` | Comment only |
| Callouts | GitHub alerts, `> [!NOTE]` | Native GFM |
| Table of contents | `[TOC]` placed on its own line | Reads as plain text |
| Footnotes, task lists, tables | Native GFM | Native |
| Math (optional, Phase 5) | `$…$` via vendored KaTeX | Reads as text |

> [!IMPORTANT]
> The extensions are the main design risk. The rule is that every `content.md` must still be valid GFM that reads well on GitHub.

### 3.3 `read.html`

- It is a static page that loads `content.md` and `style.css` via `fetch`, using relative paths. It then runs the shared `render.js`.
- The version is in `<meta name="wa-version" content="1.0.0">`, and a visible but subtle `generator` line goes in a comment.
- **Problem:** `fetch` fails on `file://`. Mitigation:
  1. The spec says "served from the directory", so fetch is the primary path.
  2. For `file://` double-click, `tools/build` and the editor's Save **inline** `content.md` and `style.css` into `<script type="text/plain" id="wa-content">` blocks as a fallback. `read.html` uses the inlined copy if fetch fails.
  3. The inlined copy is regenerated on every save. `content.md` and `style.css` remain the source of truth.
- `read.html` must not duplicate the whole runtime for every template. Either (a) the runtime is inlined once, about 60 KB with marked, or (b) it loads from a relative `../../runtime/` path. Option (a) is chosen so a `.wa` stays portable.
- It has no toolbar and no UI. The browser's own zoom, find and print are enough.
- `@media print` removes the screen chrome. Screen view shows pages as sheets on a grey backdrop. Print shows only the pages.

### 3.4 `syntax.md`

It is generated from `docs/syntax.md` and then extended with a per-template section listing that template's variables and classes. It is written so an AI agent can edit or create a template. It includes a "How to build a template" recipe, the full class vocabulary, variable reference, page-furniture examples and a validation checklist.

## 4. Editor application

### 4.1 UI

- **Logo:** custom SVG. The W's last stroke and the A's first stroke are shared and overlap, in a refined serif or didone style. It is drawn by hand as paths, not font text, so it never depends on font loading. It is also used for the favicon and PWA icons (192 and 512 px, generated with Chrome headless).
- **Menu bar:**
  - **File:** New, New from template…, Open `.wa`, Save, Save As, Import `.zip`, Export (PDF, standalone HTML, `.wa.zip`), Close.
  - **Edit:** Undo, Redo, Find and replace, Select all.
  - **Insert:** Image, Table, Link, Code block, Callout, Page break, TOC, Footnote.
  - **Format:** Bold, Italic, Strikethrough, Code, Heading levels, Lists, Quote.
  - **View:** Edit mode, Read mode, Zoom, Page grid, Dark/Light override.
  - **Templates:** Gallery.
  - **Help:** Syntax guide, Keyboard shortcuts, About and version.
- **Toolbar:** style dropdown (Paragraph, H1–H6), B, I, S, code, lists, task list, quote, link, image, table, callout, page break, undo and redo, and a template button.
- **Edit mode:** a split view. The left side has tabs for `content.md` and `style.css`, with a draggable divider. The right side is the live preview iframe. Preview updates are debounced, about 150 ms, and preserve scroll position.
- **Read mode:** hides the editor pane and centers the preview with the same renderer. Toggled with a button or `Ctrl+E`.
- **Dark/light:** `prefers-color-scheme`, with a manual override stored in `localStorage`. In dark mode the preview iframe gets `filter: brightness(.85)` so the white page is dimmed. It is applied only on the iframe element, never in exports.
- **Accessibility:** menus are keyboard navigable and have ARIA roles. The focus order is checked.

### 4.2 Core behaviors

- **Document model:** `{name, content, css, images: Map<path, Blob>, handle}`. A file tree is not needed.
- **Open:** `showDirectoryPicker()` reads the four files plus `images/`. Writes go back to the same handle. Fallback: webkitdirectory input, then Save produces a `.wa.zip`.
- **Image insert:** drag-drop or paste puts the file into `images/` (name-collision safe) and inserts `![alt](images/x.png)`. The preview resolves paths through blob URLs.
- **Autosave:** to IndexedDB every few seconds, with recovery after a crash. A manual Save writes to disk.
- **Templates gallery:** a grid with thumbnails (pre-rendered PNG of page 1, generated by `render_check.py`), category filters and search. Each card has two actions:
  - **Preview with template content:** loads the template's own sample content.
  - **Apply style to my document:** copies only `style.css` and any template fonts and images, and leaves `content.md` alone. The user's content is previewed instantly and can be undone.
- **Export:**
  - **PDF:** open the render in a hidden iframe and call `print()`. The user chooses "Save as PDF". The page-size CSS comes from `style.css`.
  - **Standalone HTML:** one file with inlined CSS, images as data-URIs, fonts subset or base64 and the renderer, with no network.

### 4.3 Offline

- `sw.js` precaches the shell, `runtime/`, `vendor/`, the fonts and the template index. Template folders are cached on the first load (about 100 × ~30 KB) in the background after the shell is ready.
- Cache name is `wa-<VERSION>`. A new version shows an "Update available, reload" toast, and old caches are deleted.
- Test: load once, go offline in Chrome DevTools or headless, and confirm that everything works.

## 5. Templates (the cornerstone)

**Requirement:** at least 100 distinct, LaTeX-quality templates, each with at least 3 pages of content.

### 5.1 Strategy

Hand-writing 100 CSS files is infeasible and would be inconsistent. Instead:

1. **Design a rich variable system** (Layer 1 above), plus about 12 reusable **style "archetypes"** (structural CSS modules): academic-paper, book, report, letter, resume, newsletter, magazine, brief or memo, presentation-handout, poster-ish, manual or docs, journal or diary.
2. **`tools/gen_templates.py`** takes a spec (archetype, palette, font pairing, details such as heading style, rules, drop caps, small caps, columns, header and footer) and **emits a complete, standalone, readable `style.css`**. The output has no `@import` of generator internals. It is plain CSS that users can read and edit.
3. Each template is then **eyeballed and tuned by hand** via screenshots. Generated does not mean unreviewed.

### 5.3 Per-template requirements (enforced by `validate.py`)

- All four files and a `syntax.md` are present, `read.html` is present, and `images/` has at least one asset where the content references one.
- `content.md` is realistic, **purpose-appropriate sample content** that fills at least 3 rendered pages (checked by headless Chrome page count, not by word count). It exercises the headings, lists, a table, a quote, code where relevant, a callout and an image. Each archetype has its own content, not 110 copies of lorem ipsum. Content is generated per archetype, with each template varying the title and metadata.
- It prints to PDF at the declared `--page-size` with no clipped content, no orphaned headings (`break-after: avoid`) and no blank pages.
- It passes a WCAG AA contrast check on text and background, in light mode.
- The `style.css` is valid and heavily commented, so beginners can find what to edit.

### 5.4 Fonts

Bundle about 25 open-license (OFL) families as woff2, Latin subset, for example: EB Garamond, Cormorant, Libre Baskerville, Crimson Pro, Playfair Display, Lora, Merriweather, Source Serif 4, Inter, Source Sans 3, Work Sans, Montserrat, Raleway, IBM Plex (Sans, Serif, Mono), JetBrains Mono, Space Grotesk, Special Elite, Courier Prime, Oswald, Bebas Neue and Caveat. Total target is under 6 MB, loaded lazily per template and cached by the service worker.

> [!WARNING]
> Fonts are the largest asset and licensing risk. Only OFL or Apache fonts are used. Each license file is shipped in `runtime/fonts/LICENSES/`. Fetching them needs network access.

## 6. Syntax guide (in-app and `docs/syntax.md`)

A single source of truth, rendered inside the editor by the **same renderer** (the guide is itself a `.wa` document and demonstrates itself). It opens from Help → Syntax guide as a read-only Read mode tab. Contents:

1. Quick start, in 5 minutes.
2. The `.wa` format and why it's a folder.
3. Every GFM element, shown as source next to rendered output: headings, emphasis, lists, task lists, links, images, code, tables, blockquotes, footnotes, alerts, rules, escaping, autolinks.
4. WA extensions: front-matter, classes, page breaks, TOC.
5. `style.css`: the variables, the class vocabulary, `@page`, fonts, columns, headers and footers, drop caps, with examples.
6. Building your own template from scratch, and a 10-minute recipe.
7. Exporting and printing tips, such as margins and background graphics.
8. A troubleshooting section.
9. "For AI agents": the section that tells an assistant the rules and a checklist.

## 7. Phased milestones

| Phase | Deliverable | Exit criteria |
|---|---|---|
| **0. Spec** | `docs/format.md`, class vocabulary, variable list, extension syntax, directory layout, `VERSION` | Reviewed and frozen for 1.0 |
| **1. Runtime** | `render.js`, `base.css`, `read.html` template, vendored marked and DOMPurify, 2 hand-made templates | `read.html` renders from `http://` and `file://`, and print-to-PDF matches the preview (pixel diff via Chrome headless) |
| **2. Editor MVP** | Shell, split view, CodeMirror, live preview, open/save directory, edit and read modes, dark mode | Open a `.wa`, edit, save, reopen with no data loss |
| **3. Menus, toolbar, export** | Full menu bar and toolbar, image insert, PDF and HTML export, zip fallback | All commands work, and the standalone HTML opens with no network |
| **4. Template system** | `gen_templates.py`, archetypes, fonts, gallery UI, preview and apply modes, `validate.py`, `render_check.py` | 12 archetypes producing about 25 validated templates |
| **5. Scale to 100+** | Fill out the catalog, tune each by hand via screenshots, thumbnails, optional math | At least 100 templates pass validation, 3 or more pages each, and look distinct |
| **6. Offline and PWA** | Service worker, manifest, icons, update flow | Passes the offline test, and an update toast is shown on a new version |
| **7. Syntax guide and polish** | Guide as a `.wa`, `syntax.md` in each template, a11y and keyboard pass, perf pass | Guide covers all of §6, a Lighthouse PWA and a11y check is clean, and a cold load is under 2 s on localhost |

Phases 4 and 5 are the bulk of the effort and are well suited to parallel work. Once the archetypes and generator exist (end of Phase 4), the catalog can be split by category and handed to several subagents or a `/swarm`. Each one would own a category's specs and be judged by `validate.py` and `render_check.py`.

## 8. Verification plan

- **Automated (Python and headless Chrome)**
  - `validate.py` checks structure, all four files, relative links, image existence, front-matter, CSS parses, and that variable names are in the vocabulary.
  - `render_check.py` prints every template to PDF and PNG with `google-chrome --headless --print-to-pdf`. It asserts a page count of at least 3, no overflow and no blank pages, and writes thumbnails and a contact sheet.
  - A preview-versus-print fidelity check on a sample of templates compares screenshots of read mode and PDF page 1 within a tolerance.
  - A browser test driver (Chrome DevTools Protocol via a small Python websocket script) runs open, edit, save and export flows, and the offline test.
- **Manual:** review the contact sheet by eye in batches, check the dark-mode dimming, and try Firefox and Safari for the fallback path.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Preview and print differ (the biggest promise in the spec) | A single renderer, print-first CSS (`@page` as the layout truth, screen view as sheets), and an automated diff check |
| `file://` blocks fetch | Inlined fallback blocks in `read.html` |
| File System Access API is Chromium-only | Zip import and export fallback and an honest notice |
| 100 templates look samey | Archetype structure, distinct palettes, fonts and ornaments, plus a contact-sheet review for near-duplicates |
| Pagination limits in browser CSS (running headers, footnotes at page bottom) | Use `@page` margin boxes (Chromium supports them) and keep footnotes as endnotes in v1 |
| Tooling creep | Node is dev-only and the shipped app needs no build. Vendored outputs are committed. |
| Offline cache size | Lazy per-template caching, woff2 Latin subsets |

## 10. Decisions (resolved)

1. **Network and tooling:** the npm registry is reachable, so vendor marked, DOMPurify, CodeMirror, fflate and fonts. Node v26 is installed user-level at `~/.local/node` (add `~/.local/node/bin` to PATH). Git still needs `sudo apt-get install -y git`.
2. **Browser target:** Chromium-first, with a zip import/export fallback elsewhere.
3. **Math:** not in 1.0 ("latex-like" means the look). It can come later as optional KaTeX.
4. **Template catalog:** about 110 templates, built in the order of §5.2.
5. **Default page size:** Letter, set per template.
